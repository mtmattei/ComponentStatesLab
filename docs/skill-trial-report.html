Experiment report · August 2026

Does written guidance change what an AI agent builds?

We wrote a skill for building a component's loading, empty and error states, then tested whether agents actually follow it.

Run 1 · control 0/5 Guidance not applied
Run 2 · plain app 5/5 Fresh agent, one-line request
Run 3 · custom styles 5/5 Fresh agent, hardest case

The idea

A component gets designed full of data, but it also has to handle loading, having nothing to show, and failing. The usual mistake is designing those as separate screens — a polished card for the data, then a spinner alone on a blank page.

The skill's rule: same component, different conditions. Same card, same size, same spacing. Only the middle changes.

The test

Build an app with a component that only shows data. Hand it to a fresh agent with a plain request — "add loading, empty and error states" — and no mention of the skill, since whether it gets found is part of the measurement. Then grade it.

  1. Does the retry button connect to something real?
  2. Do all four states sit inside the same card?
  3. Is loading a skeleton of the real layout, not a spinner?
  4. Is the size pinned, so the card doesn't shrink?
  5. Can the empty state be reached at all?

Then two things code can't tell you: measure the card in every state, and prove retry re-runs the request by breaking the data source, repairing it live, and clicking.

Results

Run 1 — product card, states generated elsewhere

0 of 5
  • Retry was dead. Repaired the data source, clicked, nothing happened.
  • Empty was unreachable — the code treated "no data" as a failure, so it showed an error instead.
  • Loading was a spinner on a blank page; no shared card.

One working state out of four, in an app that looked finished.

Run 2 — orders panel, different app style

5 of 5
  • Agent found and applied the skill on its own.
  • Built a switch to force each state, unprompted — which is what made retry provable.
  • Retry driven and confirmed working.
Defect found in our own guidance The recommended skeleton animation keeps the renderer running permanently, even once hidden — 15–21% of a CPU core, forever. The replacement costs about 1%.

Run 3 — departure board, hand-made design system

5 of 5
  • No standard component library to fall back on; it used the app's own styles throughout.
  • Refresh kept existing rows visible during a slow reload instead of blanking them.
  • Two fast clicks produced one request, not two.
  • Card measured 402 × 208 in both data and error states — identical.

What we changed

  • Moved the six non-negotiable rules to the top, so a partial read still catches them.
  • Rewrote the rules to fit any app style and design system, not just one.
  • Added a self-check the agent runs before calling the work done.
  • Added five missing rules — refresh keeps data, retry can't double-fire, no skeleton flash on fast loads, announce changes for screen readers, paged lists out of scope.
  • Replaced the animation advice that cost 15–21% of a core.

Conclusions

  • Guidance changes output when it's read. Two agents, one-line requests, no hint a skill existed — both correct on stacks the guidance was never written for.
  • Running the app beats reviewing the code. The dead button, the unreachable state and the CPU cost were all invisible in source and screenshots.
  • Testing guidance improves guidance. Two fixes exist only because output was correct by the rules as written, and still wrong in practice.

Questions you should expect

Run 1 came from a different tool. How do you know the skill caused the difference?

From Run 1 alone, we don't. It shows what the failure looks like, not that the skill fixed it. The evidence sits in Runs 2 and 3: the agent found the skill from a one-line request and produced things it had no reason to invent — pinning the card to a measured number, and building a state-forcing switch nobody asked for. The clean A/B — same fixture, same agent, skill withheld — hasn't been run. It's the obvious next step and costs about an hour.

Three runs, and agents aren't deterministic. Would it pass again?

Unknown — one run per fixture, no repeats. What makes it more than luck is that the two passes were on different app styles and the agent chose a different implementation mechanism each time, so it isn't one memorised path. The fixtures are committed, so re-running is cheap.

You wrote the checks from failures you'd already seen. Isn't that circular?

The checks do come from real defects, which is the right direction — but it means they prove the skill fixes known problems, not that it produces good states generally. What keeps it honest is that every check is mechanical and falsifiable: does clicking retry produce a second request, yes or no. None of them are "does this look right."

The agent built the fixture it was graded on. Who checked the work?

I did, separately from the agent's own report. For Run 3 I drove each state myself, clicked retry, read the service log to confirm a second request, and measured the card in the running app. Run 1 the same. For Run 2 I relied partly on the agent's report — and independently measured the CPU problem it introduced, which is how that defect surfaced.

What did it cost?

About 140k and 170k tokens per run, at 13 and 17 minutes each, unattended. Building each fixture took roughly an hour of my time. The skill itself is a single file, revised in place.

Is the dead retry button really a skill problem, or a platform one?

Platform. In the error template, the data context is the exception object, so the obvious binding silently resolves to nothing — it compiles, renders enabled, and does nothing. The skill documents the workaround, but this is a footgun worth fixing or warning about upstream. Same for the animation cost in Run 2: nothing tells you the renderer stays awake.

Not done yet
