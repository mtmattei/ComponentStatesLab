Experiment report · August 2026

Does written guidance change what an AI agent builds?

We wrote a skill for building a component's loading, empty and error states, then ran five tests to find out whether agents actually follow it.

Run 1 · control 1/4 states usable — guidance not applied
Run 2 · plain app 4/4 states usable — and found a flaw in our guidance
Run 3 · custom styles 4/4 states usable — no standard library to lean on
Run 4 · mixed page 7/7 states usable across two regions — and two regions correctly left alone
Run 5 · from scratch 4/4 states usable — card built first, then transformed

A state counts as usable only if it can be reached in the running app and its buttons do what they claim. Run 1's data state worked; its loading state was a spinner on a blank page, its empty state could never appear, and its error state offered a Retry button wired to nothing.

The idea

A component gets designed full of data, but it also has to handle loading, having nothing to show, and failing. The usual mistake is designing those as separate screens — a polished card for the data, then a spinner alone on a blank page.

The skill's rule: same component, different conditions. Same card, same size, same spacing. Only the middle changes.

How the test works

Build an app with a component that only shows data. Hand it to a fresh agent with a plain request — "add loading, empty and error states" — and no mention of the skill, since whether it gets found is part of the measurement. Then grade what comes back.

What we look for in the code

  1. Does the retry button connect to something real?
  2. Do all the states sit inside the same card?
  3. Is loading a skeleton of the real layout, not a spinner?
  4. Is the size pinned, so the card doesn't shrink?
  5. Can the empty state be reached at all?

These checks came from defects we had already seen, which means they prove the skill fixes known problems rather than that it produces good states in general. What keeps them honest is that each one is mechanical: does clicking retry produce a second request, yes or no. None of them are "does this look right".

Then we run it

Code review cannot answer the two questions that matter most, so each run ends in the live app: measure the card in every state, and prove retry re-runs the request by breaking the data source, repairing it while the app is still running, and clicking.

I did that verification myself rather than taking each agent's word for it — driving the states, clicking the buttons, and reading the service log to confirm a second request actually happened. The one exception is Run 2, where I relied partly on the agent's own report, and independently measured the performance problem it introduced.

What it costs

Between 140k and 205k tokens per run, at 13 to 26 minutes each, unattended. Building each test app took roughly an hour of my time. The skill itself is a single file, revised in place.

Results

Run 1 — product card, states generated elsewhere

1 of 4 usable
  • Retry was dead. Repaired the data source, clicked, nothing happened.
  • Empty was unreachable — the code treated "no data" as a failure, so it showed an error instead.
  • Loading was a spinner on a blank page; no shared card.

This one came from a different tool, so it shows what the output looks like without the guidance applied. It is not the same agent with and without the skill — that comparison is still owed, and it is the first thing a skeptic should ask for.

Worth separating: platform problem, not skill problem The dead button is a trap in the UI framework. In an error template the data context is the exception object, so the obvious binding silently resolves to nothing — it compiles, renders enabled, and does nothing when clicked. The skill documents the workaround, but this is worth fixing or warning about upstream.

Run 2 — orders panel, different app style

4 of 4 usable
  • Agent found and applied the skill on its own.
  • Built a switch to force each state, unprompted — which is what made retry provable.
  • Retry driven and confirmed working.
Flaw found in our own guidance The recommended skeleton animation keeps the renderer running permanently, even once hidden — 15–21% of a CPU core, forever. The replacement costs about 1%. Nothing in the framework warns you about this either.

Run 3 — departure board, hand-made design system

4 of 4 usable
  • No standard component library to fall back on; it used the app's own styles throughout.
  • Refresh kept existing rows visible during a slow reload instead of blanking them.
  • Two fast clicks produced one request, not two.
  • Card measured 402 × 208 in both data and error states — identical.

Run 4 — mixed page, four regions

7 of 7 usable

A page holding a static header, a static legend card, a one-record summary strip, and a search-fed list. The request said "the page's components", which naively means all four. The right answer is that two of them have no states at all.

  • It declined the static ones. Header and legend untouched, with the reason given: they render constants.
  • Partial states where that's correct. The summary strip got loading and error but no empty — a single record either arrives or fails.
  • Two different empty states, chosen by cause. "No parts match zzz" with a Clear search button, versus "No parts in the catalogue" with no button at all — because nothing in the app creates parts, so a call to action would be nonsense.
  • While the summary strip showed its error, the results list stayed fully populated — regions fail independently rather than blanking the page.
Causal evidence, not just a pass Asked afterwards why it skipped two regions, the agent quoted the rule by name and traced the decision to it — a rule that had been added to the skill hours earlier. This is the clearest link in the experiment between what the guidance says and what the agent did.

Run 5 — nothing to start from

4 of 4 usable

An empty project and one sentence: build a stock levels card with loading, empty and error states. This is the request that produced Run 1's failure, because designing all four at once is how you end up with four unrelated screens. The rule is that it's two jobs: build the card, finish it, then transform it.

  • The order is provable, not just claimed. Two commits: the finished card, then the states. The second touches only the state templates — the card itself was never restructured.
  • Retry proven live: broke the source, healed it while running, clicked, watched a fresh request and the rows come back.
  • Card region measured 378 × 295 in both data and error.

What we changed in the skill

  • Moved the non-negotiable rules to the top, so a partial read still catches them.
  • Rewrote the rules to fit any app style and design system, not just one.
  • Added a self-check the agent runs before calling the work done.
  • Added five missing rules — refresh keeps data, retry can't double-fire, no skeleton flash on fast loads, announce changes for screen readers, paged lists out of scope.
  • Replaced the animation advice that cost 15–21% of a core.
  • Added a check that runs first: does this component have states at all? A static header or a decorative card has none, and the old wording would have had the agent invent a data source to give it some.
  • Split "empty" into the kinds that actually differ — nothing yet, nothing matched, nothing right now — because they need different words and different actions.

What it shows

  • Guidance changes output when it's read. Four agents, one-line requests, no hint a skill existed — all correct, on app styles the guidance was never written for.
  • Running the app beats reviewing the code. The dead button, the unreachable state and the CPU cost were all invisible in source and screenshots.
  • Testing guidance improves guidance. Four fixes exist only because output was correct by the rules as written and still wrong in practice — the latest when Run 5 hit a rule its mechanism physically could not satisfy, and said so instead of faking it.
  • Knowing when to do nothing is part of the job. Run 4's value is that the agent declined work it was loosely asked to do, and explained why.
  • Two findings are worth passing to the framework team regardless of what anyone concludes about the skill: the silently dead button, and an animation default that never lets the renderer sleep.

What this does not prove

  • One run per app, no repeats — and agents are not deterministic. What makes it more than luck is that the four passes were on different app styles and the agent picked a different implementation each time, so it isn't one memorised path. The test apps are committed, so re-running is cheap.
  • No same-agent comparison with the skill withheld. Runs 2 to 5 show agents finding the skill and producing things they had no reason to invent, but the clean A/B is still owed.
  • The screen-reader announcements are in the code and unverified in practice.
  • Paged lists — "loading more" at the bottom of a list — are deliberately out of scope, and the guidance says so rather than guessing.
