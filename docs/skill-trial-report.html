Experiment report · August 2026

Does written guidance actually change what an AI agent builds?

We wrote a skill that teaches a coding agent how to build the loading, empty and error states of a UI component — then ran three tests to find out whether it makes any difference.

The short version

Three runs. One where the guidance clearly wasn't applied, which scored 0 of 5. Two where a fresh agent picked up the skill from a plain request and scored 5 of 5, on app styles the guidance was never written for.

The tests also found two real defects in the guidance itself. Both are now fixed. Every serious fault we found — in the output and in the skill — was invisible in the code and only showed up by running the app.

What the skill does

Most components get designed in one condition: full of data. But the same component has three others to handle — while the data is loading, when there is nothing to show, and when loading failed.

The usual mistake is to treat those as three separate screens. You end up with a nicely designed card for the data, and then a loading spinner floating alone on an empty page. Nothing looks related.

The skill's core rule is that these are the same component in different conditions. Same card, same size, same spacing, same typography. Only the middle changes.

Why it needed testing

A written skill can look excellent and change nothing. The agent might never read it, or read it and fall back on habit anyway. The only way to know is to look at what actually gets built — and then run it, because the worst faults don't show up on screen.

The clearest example is a "Retry" button in an error state. It can compile, look correct, and be reported as working while being connected to nothing at all. Clicking it does nothing. No code review or screenshot catches this. You only find it by clicking it.

How the test works

Build a small app with a component that shows data and nothing else. Hand it to a fresh agent with a plain request — "add loading, empty and error states" — and no mention of the skill, since whether the agent finds it is part of what we're measuring. Then grade what comes back.

Five checks on the code

  1. Does the retry button connect to something real?
  2. Do all four states sit inside the same card?
  3. Is loading a skeleton of the real layout, rather than a spinner?
  4. Is the size pinned, so the card doesn't shrink when data is absent?
  5. Can the empty state actually be reached at all?

Then two checks the code cannot answer. Drive the running app into each state and measure that the card is the same size in all of them. And prove the retry button really re-runs the request, by breaking the data source, clicking retry, and watching for a second request.

The three runs

Run 1 · control

Product card, states generated elsewhere

0 of 5

Reactive app style · standard component library

The retry button was dead. We confirmed it by breaking the data source, repairing it while the app ran, then clicking retry: nothing happened, and the app stayed stuck on the error message. The empty state could never appear at all, because the code treated "no data" as a failure — so asking for an empty result produced an error screen. Loading was a spinner on a blank page.

Net result: one working state out of four, in an app that looked finished.

Run 2 · first real test

Orders panel, plain app structure

5 of 5

Different app style · different component library

The agent found and applied the skill on its own from a one-line request. It also built a switch to force each state on demand without being asked, which is what made the retry proof possible in the first place. Retry was driven and confirmed working.

Defect found in our own guidance The skill recommended an animation technique for the loading skeleton that keeps the app's renderer running permanently — even after the animation stops and the skeleton is hidden. Measured cost: 15–21% of a CPU core, doing nothing, forever. The replacement method costs about 1%. The guidance was rewritten.
Run 3 · hard case

Departure board, hand-made design system

5 of 5

Standalone control · no standard component library at all

This app used its own hand-written colour and text styles, so there was no familiar library for the agent to fall back on. It also already had a working Refresh button, which is a trap: refreshing should keep the visible data on screen, not blank it back into a skeleton.

It handled all of it. Refresh kept the rows visible during a slow reload. Two fast clicks produced one request rather than two. The card measured 402 × 208 in both the data state and the error state — identical, which is the whole promise of the skill.

Every rule we had added to the skill that same day showed up in the result.

What we changed in the skill

  • Moved the six non-negotiable rules to the top, so a partial read still catches them.
  • Rewrote the rules so they apply to any app style and any design system, rather than assuming one.
  • Added a five-point self-check the agent runs on its own output before calling the work done.
  • Added five missing rules: a refresh keeps existing data on screen, retry can't be double-clicked into two requests, don't flash the skeleton on fast loads, announce state changes for screen readers, and paged lists are out of scope.
  • Replaced the animation advice that cost 15–21% of a CPU core.
  • Cut a large block of duplicated rules, so each rule now lives in exactly one place and can't drift out of sync.

What it shows

Written guidance does change output — when it's read. Two independent agents, given a one-line request and no hint that a skill existed, produced correct and genuinely working results on app styles the guidance was never written for.

Running the app is worth more than reviewing the code. The dead button, the unreachable empty state and the CPU cost were all invisible on the page and in the source. All three were found by running it.

Testing the guidance improves the guidance. Two of the fixes above exist only because a test produced output that was correct by the rules as written, and still wrong in practice.

Honest limits

  • Three runs is a useful signal, not a statistical sample.
  • The screen-reader announcements are in the code but haven't been checked with an actual screen reader.
  • The skeleton timing behaves sensibly but wasn't measured to the millisecond.
  • The first run was generated in a different tool, so it shows what happens without the guidance applied — not a like-for-like comparison of the same agent with and without it.
